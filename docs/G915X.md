# G915 X

The G915 X (2024) is a different keyboard from the G915: it keeps its profiles in 0x8101 onboard files, like the G515, not 0x8100. G-Lite gives it the keyboard screen through the path for other RGB keyboards (`KeyboardKinds.For`): live lighting, the Screen effect and the live effects, with its own key picture. It doesn't save to the keyboard. It has no report yet.

Sources, read on 2026-11-22:

- [TheMorpheus407/g915x-heatmap](https://github.com/TheMorpheus407/g915x-heatmap) (MIT), `PROTOCOL.md`: per-key lighting confirmed on a G915 X LIGHTSPEED (C356), from G HUB captures (OpenRGB #4461).
- [joshman1019/g915x-rgb](https://github.com/joshman1019/g915x-rgb) (MIT), `src/g915x_rgb/keyboard_layout.py`: positions and light ids of all 118 lights of the full-size board (C359), tested.
- [theo-antonescu/logi-ghub-linux](https://github.com/theo-antonescu/logi-ghub-linux) (GPL-2.0, facts only), `docs/g915x-profile-management.md`, `data/devices/046d-40b6.json`, `src/logi_ghub/layout.py`, `tests/test_profile_fs.py`: tested on a G915 X LIGHTSPEED TKL (wireless id 40B6, firmware MPK 27.00 build 0012).

## Features (G915 X LIGHTSPEED TKL)

0x0001, 0x0003 v6, 0x0005, 0x1D4B, 0x0020, 0x0007, 0x0011, 0x1004 v5 (battery), 0x8071 v4, 0x8081, 0x1B10, 0x4523 v1, 0x4540 v1, 0x8040, 0x8101, 0x1B05 v1 (key customisation), 0x8051, 0x00D0 v3 (DFU, used for custom animations), and hidden ones (0x1802, 0x1803, 0x1807, 0x1817, 0x1805, 0x1830, 0x1890, 0x1891, 0x18A1, 0x1E00, 0x1E02, 0x1602, 0x1EB0, 0x1861, 0x18B0, 0x1801). No 0x4522: the G815's Game mode list doesn't apply. 0x4523 with 0x1B10 sets the G515's (G815-G915.md, "The G515 TKL"), so the Game view picks keys the G515's way, marked experimental: not tried on a G915 X, whose control list may differ.

0x8071 has two clusters: the keys (Off, Static, Breathe 0x0A, Color cycle 0x15, Color wave 0x16, Ripple 0x17) and the logo (Off, Static, Breathe, Color cycle).

## Per-key lighting (0x8081)

- fn 1 up to four `id R G B`, fn 5 up to three ranges `first last R G B`, fn 6 one colour and up to 13 ids, fn 7 shows the frame. Sets add to a buffer; only fn 7 shows it.
- Taking over blanks every light not in the buffer. Any 0x8071 effect frame sent while streaming puts the onboard profile back and empties the buffer.
- Before streaming, G HUB takes control with 0x8071 (otherwise the media and edge lights answer error 5, Solaar #3137): fn 3 `00 00 20`, fn 5 `00 00 00`, fn 5 `01 03 07`, fn 7 `01 00 00 00 3C 01 2C`, fn 7 `01 00 00 00 00 00 5A`, fn 5 `01 03 05`, fn 3 `00 00 01`. To give the lighting back, stop driving it.
- 0x8071 fn 5 `01 03 06` claims control with the host handling power: the keyboard sends fn 1 events (`00` idle after the power-save time, `01` active) and the host turns the lights off and on with fn 8. With flags `04` only, the keyboard runs its own power-save and puts its stored lighting back over the host's colours.

## Onboard profiles (0x8101): read, not written

- fn 0 `00 00 00` answers `01 01 00 80 05 80 7F 7F 07 14 FF FF FF 20 03 07` (not decoded).
- fn 8 `<bank> <file> <size BE16>` opens a file to read, fn 12 `<offset BE16> 00` reads 16 bytes of it. Bank 0 holds the profiles in use, bank 1 the factory ones.
- File 0 of a bank is its directory: CRC32 (big-endian) over the rest, the count, then per profile `<n> 81 01 40 63 <CRC32 of the profile> <file>`, then FF. The G515's has one profile in file 08; a G915 X TKL's has three:

  `3EA1F833 03 01 81014063 FF67163E 08 02 81014063 65C92231 09 03 81014063 65C92231 0A FF`

- Profile files are 0x63 bytes, the G515's layout: two bytes (`00 01` here, `01 01` on the G515), the power-save and power-off times (BE16, 60 and 300), a 12-character UTF-16BE name ("Default co…"), then the 0x8071 records for the lighting and for power-save. G HUB's default lighting is effect 0x0C: one of the custom animations stored on the keyboard.
- fn 6 `00 00 00` asks the state: the reply starts `<mode> 00 <profile>`, mode 1 onboard and 0 while the host has it. fn 6 `05` switches to host mode, `03` back to onboard.
- fn 9 `81 01 01 00 <profile> 00 63 <CRC32>` selects a profile (the CRC its directory entry lists): the same call G-Lite's G515 code makes for its one profile. Fn+F2, F3 and F4 do the same on the keyboard, which sends fn 0 `00 <profile>`.
- G HUB in its normal mode never rewrote a profile: it sets lighting live with 0x8071 fn 1. Its writes were seen at start-up but not decoded (fn 2 `00 02 00`, fn 3, fn 9 with a 0x1B05 table, 0x8071 fn 7 `01 00 00 00 3C 01 0E` for power-save after 60 s and off after 270 s).
- Custom animations go up with 0x00D0 (DFU): fn 4 `04 <slot> "RGB_V0000"`, then the file in 16-byte packets on function n % 4. The file is a 0x4B-byte header and 17-byte 0x8081 records, padded with FF to 12304 bytes and a 16-byte trailer. Slot 0 is brightness + 8, slot 1 brightness + 9. They can't be read back.

## Saving: not done

Writing would follow the G515 (fn 2 and fn 3 to stage, fn 7 to commit a file with its CRC32, then fn 9), but into the profile the keyboard runs, with only its directory entry changed. No project has written a G915 X profile, and the G515 code assumes one profile, so G-Lite doesn't try. A report would show the directory and profiles; then one save, with a backup.

A search on 2026-11-22 found nothing that writes 0x8101 on a G915 X, and no capture of G HUB saving one. What writes 0x8101 elsewhere:

- [mevdschee/logirgb](https://github.com/mevdschee/logirgb) (MIT), `lighting/profilemgmt.go`, tested on a G515 TKL (C358) and G515 Rapid TKL (C363): the same sequence as G-Lite (fn 2, fn 3, read the buffer back, fn 7 with the CRC32, read the file back; the profile, then the directory, then fn 6 `0B`, fn 9 and fn 6 `00`). On the Rapid it changes only the active profile's entry in the existing directory (profiles of 0x6D bytes). It would refuse a G915 X: it wants one 0x8071 cluster.
- [gabriellaines/rigdeck](https://github.com/gabriellaines/rigdeck) (GPL-3.0, facts only), `docs/protocols/logitech-pro-x-tkl-rapid.md`: a decoded G HUB onboard save on a PRO X TKL RAPID (C35B). G HUB wrote an empty directory (`<crc32> 00 FF`) first, then each profile file (08, 09, 0A) and the Rapid Trigger file (0B), then the new directory; fn 2 took `<length BE16> 00`. That save put all three profiles back to their factory copies.
- What a write would have to keep: an entry's byte 3 may be flags plus the length's high bits rather than a fixed `40`; profile lengths differ (0x63 on the G515 and G915 X, 0x6D on the Rapids, 0x6F on the G512 X); directories can also list 0x1B05 and 0x1B08 files, which must be kept; factory files don't carry a plain CRC32; and after fn 9 the state reply gives the entry number, not the file.
