# Code map

What each source file holds, what it does and the protocol facts behind it. `CLAUDE.md` lists the files; keep this map up to date with the code.

- `app/Hidpp.cs`: `Hidpp`, HID++ 2.0 over the receiver, and `Register` and `Upload` for HID++ 1.0 registers and memory uploads when it's given the short collection, and its errors (`HidppError`, `RefusedException`, `HalfWrittenException`). `Call` tries a busy error (8) again after 30, 60 and 90 ms, as Solaar does (`SendRetryingBusy`); `CallUnlogged` doesn't, since live frames pace themselves. A direct device's reply at index 0x00 is taken too (over Bluetooth, per Solaar; untried). `FeatureIndex` also notes the features the device flags hidden and internal (root fn 0, byte 1 bits 6 and 5; hidden alone can mark a working feature), which `Hidden` answers
- `app/KeyboardLighting.cs`:
  - `Lighting`: the lighting settings
  - `G515Profile`: the effect table, profile encode and decode, CRC32, onboard file read and write, preview (each effect's index looked up once per connection, `EffectIndexes`)
  - `G915Lighting`: live lighting on the G915, G915 TKL and G815 (0x8071 keys and logo clusters, the older effect ids; `G915Lighting.Claim` also sets full power with fn 8, since the keyboard wakes from its own sleep in power mode 3 and ignores effects until then). Live lighting tested on a G915 TKL. The G815 is wired: 256-byte sectors, no idle times (`KeyboardKinds.NoIdleTimes` hides them, and `Build` keeps the profile's and copies records 0–1 to 2–3), and it keeps running its old copy of a profile written again until it leaves onboard mode and comes back (`Store` sends 0x8100 fn 1 `02` then `01` after the hand-back, `KeyboardKinds.ReloadThroughHostMode`). `G915Lighting.Slots` reads the enabled profiles from the directory (sector 0000, 16 bytes at a time) and the running one (fn 4); nothing when not in onboard mode. Save to keyboard writes the active onboard profile (format 4: lighting records at 0xD0, idle times at 0x1C, after a backup under `backups\<device>\`), and Backups can restore the factory copy's lighting (`FactoryLighting`), and on the G815 its G keys too, as Restore the factory profile (`FactoryButtons`); a backup is the whole sector, so it brings back the G keys with the lighting. See `docs/G815-G915.md`.
- `app/Program.cs`:
  - `MainWindow`: the device sidebar, one page per found device, rescans on plug and unplug, the Settings and Logs screens (Settings keeps its title above a `ScrollPanel`, `SettingsHeader` high, which ends with `ServicesBox`; each titled box is placed by `Section` below the one before, and every row of every box, Services' too, is `Ui.RowHeight` (64) high), updates and run on startup. `Main` hands `--services` to `LogitechSoftware.RunElevated` before anything else. A click on the G-Lite title opens `KeyboardView` with the games on its own `FakeHidpp`; it doesn't look clickable on purpose
  - The window is a standard one: Windows draws its title bar, frame and buttons, and only the title bar moves it (nothing inside the window does, so a slider dragged too far can't move or un-maximize it), the title bar in the sidebar's colour on Windows 11 and dark or light on Windows 10, without its title or icon (`StyleFrame`, `WindowHelpers.TitleBar`). The sidebar starts with the G-Lite title (`TitleLogo`), then the device list, and has no edge line; the pages' top left corner is rounded into it (`corner`, kept on top of the pages). It can be resized and maximized, down to 868 × 730 of client at 100% (`WM_GETMINMAXINFO`, with the frame it has). On `WM_DPICHANGED` it takes Windows' suggested bounds after rescaling. Once moved or resized by hand (bounds changed between `WM_ENTERSIZEMOVE` and `WM_EXITSIZEMOVE`, which a click on the title bar sends too), `ShowPanel` leaves it where it is instead of putting it at the bottom right. `OnResize` sizes the sidebar (its bottom buttons are anchored) and the shown page (`PageBounds`: it keeps its 656 width, centred right of the sidebar, and takes the window's height); a hidden page is sized when it's shown (`Watch`). Pages are laid out at `Ui.PageSize`. A device page's footer stays under its settings; on Logs, Update and the report the footer is anchored to the bottom (`Ui.Footer`) and their box grows down to it (`Ui.Tall`). Report and Backups follow the device's name (`PlaceHeaderButtons`). Logs isn't reloaded when it's already shown. `ShowPanel` shows the window with `WindowHelpers.ShowPainted`. Rescaling takes time with every page (about 0.8 s with the demo's 30, 60 ms with two devices).
  - The device list (`DeviceList` in `app/DeviceList.cs`, a `ScrollPanel`) scrolls with the mouse wheel (an eased glide) when it doesn't fit above the update row and the buttons. It has no scrollbar.
  - `Main`: the tray icon, its menu (the devices with their battery, Scan for devices, Settings, Quit G-Lite: `MenuRow` puts the value in the shortcut column) and its hover popup (`TrayTip` in `app/Tray.cs`: CPU, RAM, each device with its battery, a new version; placed over the icon from `Shell_NotifyIconGetRect`, so it stays put while the mouse moves, with small corners and the colours of the system's tooltips, which follow the taskbar's theme), the single-instance mutex and `--demo`
- `app/DeviceTable.cs`: `DeviceTable`, the device table. Each entry says which devices it matches (`FoundDevice.IsG515`, `IsMouse`…), which screen they get, how to make it (with its driver), and the fake `--demo` uses. The first match wins; asleep or unmatched devices get `InfoPage`. To add a device that works like one already supported, add an entry. For a new protocol, add a driver (like `IMouse`) and an entry.
- `app/FoundDevice.cs`: `FoundDevice`, what the scan learned about a device. `Models` holds its product IDs per connection, decoded from 0x0003 fn 0 (bytes 5–6 the connection bits: 0x01/0x02 Bluetooth, 0x04 LIGHTSPEED, 0x08 USB; bytes 7–12 one ID per set bit, in bit order), or from the USB path for HID++ 1.0 devices. Retail model numbers aren't on the device.
- `app/Devices.cs`:
  - `Devices.Scan`: finds every Logitech HID++ interface. Direct devices answer at index 0xFF. Receivers list their paired slots (register 0xB5, sub-register 0x2N; a Bolt receiver, C548, answers 0x5N instead, with the wireless id's bytes swapped and the kind in byte 1), and each slot is pinged. A slot that answers the ping with HID++ 1.0 error `01` (invalid sub-ID, how Solaar tells HID++ 1.0) is a HID++ 1.0 device at that index (`FoundDevice.Hidpp10`, named from `Devices.OldWireless` by wireless id: 1023 G700, 102A G700s). The G700's receiver (C531, link "Wireless", a Nano receiver with one device) gets slot 1 tried even if it doesn't answer 0xB5. Ports come from cfgmgr32 (`CM_Get_Device_Interface_List`), not WMI. A port with neither is tried as an old HID++ 1.0 USB device at index 0x00 (register 0xF1, firmware), like the G9x Laser Mouse: its name comes from the USB product string (`FoundDevice.Hidpp10`, `FoundDevice.ShortPath`). The G9x gets the mouse screen, others the info page. It returns every device with a name, G devices first. `LooksG` also accepts a name with the model last, like "Gaming Keyboard G213", and `ShortName` drops the front. A device without 0x0005 is named from its USB product string. `DeviceTable.For` gives G devices (`FoundDevice.IsG`: `LooksG` or a Litra) their screen from `DeviceTable.All`; other devices get `OtherDevicePage` when they have a setting it knows, else the info page, where only the report talks to them. Non-G devices whose wireless id is in `Devices.Others` get their name from it (4023, the K270/K295, see `docs/K295.md`). Their battery only reports good (30) or low (5), so `FoundDevice.BatteryGoodOrLowOnly` shows a full or low icon without a percentage. If they have 0x40A0 (`FoundDevice.MediaKeys`), the info page shows "Use F1–F12 as media keys" instead of Not supported yet: 0x40A0 fn 1 sets it, kept as `fnswap.<device>` and sent again after each scan. A Logitech audio device (USB id 0A00–0BFF) with a G name that the HID++ scan didn't find, like the G735 or PRO X 2 headsets (they use another transport), is listed the same way (`Devices.Unfound`) so its owner can send a report. So are the old G mice and keyboards in `Devices.UnfoundModels` (G5, G9, G9x, G500, G700, G300, G400, G600, G100s, MX518, G11, G13, G15, G19, G103, G105, G110, G710) when the scan didn't find them, named from `PlainNames`. The G510 and G510s (C22D, C22E) and the F310, F510 and F710 gamepads in D mode (C216, C218, C219) don't speak HID++: they are listed with `FoundDevice.PlainHid` (`Devices.PlainNames` gives their name and kind), skipped by the HID++ scan, and get the info page, except the G510 with its vendor collection, which gets `G510Page`, and the G600 with its FF80 collection, which gets `MousePage` with `G600Mouse`. See `docs/G510.md` and `docs/gamepads.md`.
  - `ScanProbe`: the scan's HID++ calls. HID++ 1.0 errors come back on the receiver's short collection.
  - Names of devices seen awake are kept as `seen.<wireless id>` in `settings.txt`, for when they're asleep.
  - An asleep receiver slot is dropped when an awake device lists its wireless id in `Models`, like a keyboard on its cable.
  - Battery: the scan finds the first of 0x1004, 0x1000, 0x1001 or 0x1F20 (`FoundDevice.BatteryFeature`, `BatteryId`) and `Devices.Decode` reads the level and the charging flag. 0x1001 byte 2: bit 7 is on external power, bits 0–2 are 1 when full. While a voltage-only device charges, its voltage says little: the level comes from a charging curve (`FoundDevice.FromChargingVolts`, a few points of G HUB's model for the G Pro Wireless, 68% at 4.2 V), and `Devices.Remember` keeps the last level read off the charger (`battery.<device>` in `settings.txt`: level, minute, charging) and counts up 1% a minute from it.
  - `DeviceWatcher` listens to each device's port and its receiver's short collection. A receiver's 0x41 (a device connected or disconnected) triggers a rescan; a connect (`Devices.LinkUp`: bit 6 of the flags byte, report[4], clear, as Solaar reads it) also calls the device page's `Reconnected`, which runs `Opened` again when `ReopensWhenFound`: a keyboard turned off and on quickly is never seen gone by a scan, yet forgets its Game mode list. A battery event (fn 0, swid 0, on the device's battery feature) updates the level. `MainWindow.ReadBatteries` reads every battery once a minute and when the tray icon is hovered (at most every 5 s), one call each.
- `app/Pages.cs`:
  - `DevicePage.UseBody`: a screen laid out in rows puts its settings on `Body.Sheet` (several views share it, showing their own sections), a `ScrollPanel` under the preset row, or lower when the screen keeps something above it. `PlaceFooter` makes Body as tall as its rows (`FitBody`, in design units) and puts the footer (status, Revert, the action button and what a screen adds with `InFooter`) right under it, or at the bottom of the window with Body scrolling when the rows don't fit.
  - `DevicePage`: what every device screen shares: the title, the presets row (–, no preset, which calls `Revert`, plus the presets, Update (New… with –, which starts Save as new), and a … menu with Save as new, Rename and Delete; a dot marks a preset changed since it was loaded or updated), the device work queue, the status line (an action button sits left of Revert, or of `FooterPicker`; with under 220 px left for the text, the action joins the text, which takes the click) with Revert (with a preset loaded: loads it again, enabled while it has the dot; with –: calls `Revert`, enabled while `Unsaved`) and the Backups menu. `RunOnDevice` opens the connection when there's none and calls `Opened` on it, for a screen with something the device forgets when unplugged; a call failing other than with a HID++ error drops it and calls `Lost`, and with `ReopensWhenFound` the next scan that finds the device (`SetFound`) opens it again at once. Presets are stored on the PC as `profile.<device>.<name>`, and the picked one as `preset.<device>` (with `=edited` once the settings moved away from it), picked again after the screen's first load (`DevicePage.LoadToSendAgain` loads each new screen that has one (`SendsAgain`) and isn't shown, at scan, in the tray too). A clean one is sent again when the device doesn't match it (a G515 or mouse comes back on its onboard lighting when the preset wasn't saved), unless the profile is damaged (`Damaged`); an edited one is only picked, with the dot. New… is enabled once the device has been read.
  - `ColorRow`: the colour swatches, your last custom colour and +, 36 apart, measured from a swatch's own width since the page may not be scaled yet. In a row of the rows layout (`alignRight`) + stays at the right edge and the swatches move left when your colour shows.
  - `InfoPage` for G devices G-Lite can't change yet or that are asleep, and `EmptyPage`
- `app/ReportView.cs`: `ReportView`, the report screen that Report opens on every device screen, with Copy and Open GitHub issue
- `app/KeyboardPage.cs`:
  - The Settings view is laid out in rows (`DevicePage.UseBody`, `Rows`): the key picture without a box, kept above Body so it stays while the rows scroll (`UseBody`'s top), then the Lighting section (Per zone and Part on a keyboard with a light bar, Effect, the Screen effect's rows while it runs (Zones with the monitor's preview, Monitor, Color boost, Update rate, Smooth changes; hidden otherwise, when `PlaceSections` moves the rows under them, the box and the section after it up, from each one's design position in `belowScreen`), Color, Solid color, Direction, Brightness, Speed, Intensity, and the two pause switches, Solid and the switches only on a keyboard with live effects) and When idle, or Saving with its note on a keyboard G-Lite can't save to. A row whose setting doesn't apply is greyed (`RowText.Enable`), never hidden. The Bindings and Game views are sections on the same sheet, one view's at a time (`PlaceSections`, which fits Body to the view): G keys, a row per key (`ButtonRows` in rows mode) with the hint on the title's line; Game mode, the note and Keys turned off with Clear, its keys picked on `gamePicture` in the lighting picture's place (`GameModeKeys.Picture`).
  - `KeyboardPage`: the screen of the RGB keyboards (the G515, G915, G815, G512 X and the others `KeyboardKinds` describes), the preview sent at most every 120 ms while a control moves (`debounce`, started only when not running; every device screen does the same); during a drag of Speed or Intensity only the values beside them change (`Changed(false, true)`, `Values`) and the whole screen with its picture is refreshed at each send, without setting a slider that's held (`Capture`), and once more when it's let go (`MouseUp`), as on `ZonesPage`; the backups menu and the offer to restore when the saved lighting is half written. Presets are `profile.g515.<name>`.
  - A keyboard with onboard profiles (`KeyboardKinds.Profile`) and two or more enabled shows them as M1, M2, M3 (sector N is MN) in a `SegmentedPicker` in the footer, left of Revert and as tall (`slotPicker`, placed by `DevicePage.FooterPicker`; `FooterPickerShown` says whether it shows, since `Visible` reads false while the window is in the tray), and Save names the running one (Save to M1). Picking one, an 0x8100 event fn 0 (`KeyboardPage.Heard`, passed by `MainWindow.Heard`) or a new fn 4 read when the window is activated (`KeyboardPage.CheckKeyboard`, from `MainWindow.OnActivated`, for an event missed or a keyboard that sends none; the G815 sends it) all go through `SlotSwitched`: the live lighting not saved is released and forgotten, the Screen effect or a live effect stops (`ScreenOff`), the preset goes back to – (`DevicePage.DropPreset`, which keeps its changes as a draft and sends nothing), fn 3 switches when picked here, Save is off until the new slot is read (it would write the old slot's lighting into it), and the screen loads the slot's saved lighting. The activation check is skipped while the keyboard is asleep, where each read takes about 3 s. Off its onboard profiles (0x8100 fn 2 isn't 1, as while G HUB runs: fn 4 then answers 0), `takenOver` hides M1–M3, turns Save off and puts a red status line (`DevicePage.ShowError`); `LoadLive` finds it when the slots come back empty, and the activation check when fn 4 answers 0, and reads the keyboard again once fn 4 names a profile (through `SlotSwitched` when it's another profile than before, as an M-key switch). See `docs/on-board-memory.md`.
  - `KeyboardKinds.GKeys` (the G815: G1–G5; experimental, `GKeysExperimental`: the G915 TKL's F1–F12 and the G915's G1–G5, shown only when 0x8100 fn 0 byte 5 counts exactly them plus M1–M3, read by `G915Lighting.ReadProfile`'s `buttons`) gives a Bindings view (`viewPick`, `views`, `openView`) and a G keys section with `ButtonRows`. `gKeys` is what's edited, `storedGKeys` what the running profile holds (`G915Lighting.ReadButtons`, read with the profile in `LoadLive`). Save writes the rows that changed with `G915Lighting.WithButtons` (bytes from 0x20, then the CRC), with the lighting only when it was changed (`dirty`), and refuses when the keyboard now runs another slot than the one the G keys were read from (`gKeysSector`). They have their own edit count (`gKeyEdits`), so a G key edit never holds back a lighting read. An M-key switch, Revert and "–" drop unsaved G key edits (`DropGKeyEdits`); with a preset picked, Revert is on for them too (`DevicePage.UnsavedBesidesPreset`, `RevertBesidesPreset`). While the Screen effect or a live effect runs they can't be changed, since Save is off. Presets leave them out (`ApplyPreset` drops a `~` and what follows, from presets saved while they kept them). They are never sent live.
  - `KeyboardKinds.GameMode` (`GameModeSupport`: `Tested` on the G815 and the G515, `Experimental` on the G915, G915 TKL, G915 X models and G512 X 75, which say so in the view's note) gives a Game view when the keyboard has 0x4522, or 0x4523 and 0x1B10 (`gameBitmap`: the list goes out as a bitmap of controls, and Windows and Menu can be picked). On the G915s the Fn key, which has the right Windows key's id, isn't hatched (`KeyLayout.KeyNames`). The Game view: the picking picture from `GameModeKeys.Picture` (in `app/GameMode.cs`) in the sticky picture's place, and a Game mode section with the note, the count and Clear (`ShowGameKeys`). `gameKeys` holds the keys the Game mode key turns off besides Windows and Menu, as USB usages. They're live, like a lighting not saved: each change sends the whole list (`SetGameKeys`, `GameModeKeys.Send`) and keeps it as `gamemode.<device>` in `settings.txt`, and `Opened` sends it whenever a connection opens, the first one and after one was lost (`ReopensWhenFound` makes the scan that finds the keyboard again open one), since the keyboard forgets it when it loses power, and again when G HUB lets go of the keyboard. `Current` ends in `!` and the usages, so presets hold them; `ApplyPreset` sets them from a preset that has the `!` and leaves them alone for an older one. A preset whose lighting is the one shown sends no lighting, so Revert after a Game mode key change, or an older preset at start, leaves the keyboard on its onboard lighting; the preset is read in full before the keys change. "–" and Revert without a preset clear them (`Forget`), and they count as `Unsaved`, so Revert is on while there are any. The view picker is right of the preset row, which reaches x 436 while a preset is named, so with three views the third is labelled Game.
  - The Effect is a `Dropdown` (`effects`, ids in `effectIds`): the keyboard's own effects, then, with 0x8081, Screen and the live effects (`LiveEffects`); Ripple is greyed out for the G512 X's light bar.
  - The live effects run like the Screen effect: `Screening` is true for both (Save off, "Live only.", the keys claimed and released, presets and `screen.on.<device>`, which holds `1` for Screen and the lighting's text for a live effect, so it starts again with G-Lite), and `Sampling` only for Screen (its rows: zones, monitor and the rest). `Animate` draws a frame every 40 ms on a cable and every 100 ms without one (`FrameInterval`) on the picture (`ShowAnimation`) and sends the keys whose colour changed by more than 9 (all of them, and the claim, every 2 s) with `KeyLights.SendColors`; without a cable at most 40 keys a frame (`WirelessKeysPerFrame`), the unsent and most changed first, the others left for the next frames (on a full frame they're dropped from `sentColors`, so they go first). A frame that fails with error 8, busy, sets `releaseFirst`: the next claim gives the lighting back to the keyboard first (`ReleaseLights`, also used when an effect stops), until a release goes through. Entering a live effect from one of the keyboard's sets the intensity to 50 (`LiveEffects.DefaultIntensity`), and leaving it resets the speed to the effect's default and the intensity to 100. The dropdown marks Screen and the live effects with a Live badge (`Dropdown.Badge`). For a live effect, the Direction row holds its own directions (`liveDirections`: Up, Down, Left, Right, Center out, Center in as Wave's 7, 2, 6, 1, 3, 8, the last two along the rows mirrored about the middle and called Out and In; for Audio, Rain and Fire, which start Up, Down and Up; `KeyField.Along` and `Lanes` turn the keys to the direction), and the two pause switches are rows of Lighting that the live effects and Screen share (`livePause`, `liveBattery`: `ScreenSettings.PauseWhenLocked` and `PauseOnBattery`; Low battery greyed out and off without 0x1004), and Audio's Solid color is a row too (`solidToggle`, `Lighting.Solid`, written after the intensity only when on; `EffectInfo.OffersSolid`). Solid is cleared when another effect is picked. The running profile's own M key sends no event and leaves the lighting's control as it was, so a live effect can't follow it; picking the running profile in the footer during a live effect goes through `SlotSwitched(again)` instead, which stops it. The period and intensity a live effect set are reset when a keyboard effect is picked next, even through Screen (`liveSettings`), and its direction too when the keyboard's Wave doesn't have it (to Right). Positions set after the page is built (the rows under Screen's) use `DevicePage.Scaled`, from the page's width, since the page is scaled as a whole once placed. Audio clears its samples when loopback sends nothing for 150 ms, as it does while nothing plays. Timers don't run in the traces (`DevicePage.Manual`).
  - `KeyboardKinds.VerticalWave` (the G815) adds Up (direction 7), Down (2) and All (0) to the Wave directions (`directionValues`). Another 0x8071 keyboard gets Up and Down, not All, once its Wave lists vertical capability bits (0x0040, 0x0800), read by `G915Lighting.Clusters` at the first load (`verticalWave`, `ApplyWaveDirections`): the G515, G915 TKL and G512 X 75 report them. With Up and Down, the Direction row names Center out and Center in Out and In, so six or seven cells fit (`DirectionNames`).
  - `KeyboardKinds.Intensity` (the G815) adds an Intensity slider for Breathe, Cycle and Wave; keyboards with 0x8081 have it for the live effects (their density, height, spread or colour mix, still labelled Intensity) (`Lighting.Intensity`, written in `lighting.<device>` and presets only when it isn't 100, so older texts stay the same; `G915Lighting.Encode` sends it, at least 1 since 0 shows as 100, `Decode` reads it with 0 as 100; the power-save records take a percentage of it).
  - `KeyboardKinds.BrightnessLevels` (the G815: 0, 12, 25, 50, 100) become the Brightness sliders' `Stops`, and a preset's brightness drops to the level below (`KeyboardPage.Allowed`), as the keyboard does.
  - The brightness key: an 0x8040 event fn 0, or a new 0x8040 fn 1 read at activation (`CheckKeyboard`, skipped while an edit waits to be sent), sets the Brightness slider (the Screen effect's too), the remembered `lighting.<device>` level (not while the Screen effect runs, which would remember it) and the preset's dot, without sending anything.
  - Without idle settings (`KeyboardKinds.NoIdleTimes`, the G815) there's no When idle section.
  - A keyboard with `KeyboardKinds.Bar` (the G512 X 75's light bar ids) gets Per zone and Part rows at the top of Lighting (`KeyboardPage.part`): the bar's own `Lighting` (`bar`, null while the toggle is off) goes to the other 0x8071 clusters (`G915Lighting.Preview`'s `others`), and is written after a `#` in `lighting.<device>` and presets. `KeyPicture.Bar` and `Focus` draw each part with its own effect and dim the other; a click on the picture picks the part. the Effect dropdown's `Off` greys out Ripple for the bar.
  - A keyboard that doesn't save (the G915, the G512 X 75) has no Save, Backups or idle settings. It keeps the lighting as `lighting.<device>` in `settings.txt` and sets it again on each load, on every 0x8071 cluster (`G915Lighting.Clusters`, `G915Lighting.Pick`: a cluster without the effect gets a close one). Presets are `profile.g915.<name>` and `profile.g512x.<name>`. See `docs/G512X.md`.
- `app/GameMode.cs`: `GameModeKeys`, the Game mode key's list (0x4522, [G815-G915.md](G815-G915.md), tried on the G815; the format from OpenLogi): fn 3 clears it, fn 1 adds up to 16 USB usages per call, ended by `00` unless the call is full (`Packets`). The firmware turns off the Windows and Menu keys itself (`AlwaysOff`, which can't be picked), and the list only applies while Game mode is on. On 0x4523 keyboards (the G515, tried; the G915 X) `Send` with `controlBitmap` writes 0x4523 fn 0 with a 16-byte `Bitmap`: bit i for the keyboard's control i, from the control list 0x1B10 gives (`Controls`, read once per connection), each control id mapped to a usage by `ControlUsages`. There Windows and Menu stay on unless picked (`CanPick(usage, true)`: any usage with a control). `Usage` and `LightingId` convert between a key's lighting id and its usage (usage minus 3; the modifiers 0x68–0x6F are E0–E7; the G, M, media and brightness keys have none, which matches G HUB). `Split` takes the keys off the end of a preset (after the last `!`). `Typed` gives what a letter, digit or punctuation key types with the Windows layout in use (its set 1 scan code through `MapVirtualKeyEx`), so the picture shows a Swiss keyboard's Z where the layout file has Y. `GameModeKeys.Picture`: the picture to pick the Game view's keys on (Win and Menu hatched unless `controlBitmap`), for `KeyboardPage` and `ZonesPage`, which keep the list in settings and presets and send it.
- `app/KeyboardKinds.cs`:
  - `KeyboardKinds`: what differs between the keyboards on the keyboard screen (`KeyboardPage`), given by their `DeviceTable` entry: the key map (and the ISO one, picked when 0x4540 reports a layout of 2 or more, `KeyLayout.IsIso`), the preset prefix and whether it saves.
  - `KeyboardKinds.For`: any other G keyboard with 0x8071 and 0x8040 (`FoundDevice.IsRgbKeyboard`, after the entries above in `DeviceTable`) gets live lighting with a key map picked from its name (`KeyboardKinds.File`: G915 X, 60, 75, 98, else TKL; `g-full.json` and `g-60.json` are generic), titled with its own name, and a note that the picture is a guess, except the G915 X's `g915-x.json` and `g915-x-tkl.json`, from projects that lit every id (`docs/G915X.md`). The G515 RAPID TKL goes this way, not through `IsG515`.
- `app/KeyPicture.cs`: `KeyPicture`, the live key picture (the keyboard screens: `KeyboardPage`, `ZonesPage` (the G213, G413, G512, G513, G PRO keyboard, G410, G810 and G910) and `G510Page`). A key without a lighting id (`--`, like the G815's M1–M3, MR and Game mode keys) is drawn but stays dark. In picking mode (`Picking`, the Game view) it doesn't animate: each key shows its name (`Label`, else the layout's), picked keys (`PickedIds`) are filled with the accent, fixed ones (`FixedIds`) hatched, keys `CanPick` refuses are dimmed, a pickable key under the pointer is lit (`hovered`), the key named `GameModeKey` is outlined with a joystick drawn on it, and a click on a pickable key raises `IdPicked` with its lighting id. `PickedText` and `PressKey` are for the traces.
