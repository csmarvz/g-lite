# G510 and G512 X 75 support

The G510 / G510s, and the plan that came before the G512 X 75's support. The G510 hasn't been on this PC: its screen is built from an owner's report and the Linux driver, not checked on a real keyboard yet.

## G510 / G510s

USB 046D:C22D, and C22E with its headset audio turned on. A 2010 keyboard. It doesn't speak HID++: G-Lite's HID++ scan skips it, and it goes through feature reports instead.

From the Linux driver `drivers/hid/hid-lg-g15.c` (GPL: only the facts are used here, no code), added in 2019 by Hans de Goede:

| Feature report | What |
|---|---|
| 0x04 | M1, M2, M3 and MR key LEDs, one bit each |
| 0x05 | Backlight colour, `05 R G B`. The driver reads it with GET_REPORT and sets it with SET_REPORT, 4 bytes. |

- The backlight is one colour for the whole keyboard. There's no hardware brightness: the driver scales R, G and B itself.
- The keyboard has its own light button that turns the backlight on and off.
- The LCD (160×43, mono) and the G-keys are separate. The LCD is left out; the G keys are below.
- LGS lists the G510 on usage page 0xFF00 ([research/lgs-manifest-inventory.md](research/lgs-manifest-inventory.md)).

### The G510s's report

From an owner (G-Lite 0.0.26-alpha, 2026-11-14), USB 046D:C22D:

| Collection | Usage | Reports |
|---|---|---|
| MI_00 | 0001:0006, the keyboard, held by Windows | input 9, output 2 |
| MI_01&COL01 | 000C:0001, media keys | input 2 |
| MI_01&COL02 | FF00:0000, vendor | input 8, output 992, feature 258 |

The vendor collection's feature reports, read with `HidD_GetFeature`:

| Id | Bytes after the id | What |
|---|---|---|
| 0x01 | 18, zeros | Unknown |
| 0x03 | 20, zeros | Unknown |
| 0x04 | `80` | M-key lights: M1 lit, so M1 is bit 7 |
| 0x05 | `FF FF FF` | Backlight colour, white |
| 0x06 | `FF FF FF` | A second colour. Probably the one the keyboard starts with; not written by G-Lite |
| 0x07 | `03 00` | Unknown |
| 0x08 | 257 | "SGL", "EMAN", "G510s" in UTF-16, then zlib data: looks like a firmware or LCD resource |
| 0x09, 0x80 | error 31 | Can't be read |

### The screen

`G510Page` (for `FoundDevice.IsG510`: a plain HID G510 whose vendor collection was found, `FoundDevice.HasVendorCollection`, which is then its `Path`): an effect (Off, Static, Breathe, Cycle), a colour, brightness and speed. Brightness is scaled into the colour, sent as `05 R G B` with `Hidpp.SetFeature` on the vendor collection. Off sends `05 00 00 00`. The keyboard has no effects of its own (none in the report, the Linux driver or LGS), so Breathe and Cycle are run by G-Lite, as on the Litra: `G510Lighting.Frame` works out the colour, and a 50 ms timer sends it with `Hidpp.SetFeatureUnlogged` (kept out of the log) only when it changed. They stop when G-Lite quits; off in traces (`DevicePage.Manual`). On load it reads 0x05 to show the colour that's on. Live only: kept as `lighting.<device>` and set again on load. Presets. Revert (or the – preset) goes back to the colour read at load. Tested against `FakeG510`, built from the report.

The screen is laid out in rows like the other keyboards, with a picture of the keyboard (`app/models/g510.json`, from a photo: G1 to G18 at the left, the M keys, Game mode switch, headset and mic buttons and light button along the top, the media keys, Mute and the volume roller above the numpad; the LCD is a gap).

M1, M2 and M3 are in the footer, like the G815's onboard profiles. Each has its own lighting and G key bindings, as LGS kept them. Picking one in G-Lite lights it (feature 0x04) and sends its lighting, or, when it has none of its own, the colour the keyboard had when G-Lite first read it. On load the screen starts on the M key the keyboard has lit (feature 0x04 read). Pressing an M key on the keyboard switches nothing yet (below). Presets hold the three M keys' lighting (an older preset's one lighting goes to M1). Three views:

- Settings: Effect, Color, Brightness, Speed, and a note that G-Lite can't save to the keyboard.
- Bindings: G1 to G18 for the M key picked, kept in G-Lite's settings (`gkeys.<device>.m1` to `.m3`): the keyboard keeps none. MR isn't used. Nothing reads the G keys yet, so the bindings do nothing (below).
- Game: the keyboard turns its Windows keys off itself while its Game mode switch is on; there's no list of keys to pick. The switch's state is read when the view opens, from input report 0x03 asked for once (`HidD_GetInputReport`).

### The G keys, M keys and Game mode switch

From hid-lg-g15 (facts only): input report 0x03, 5 bytes with the id, on the vendor collection. G1 to G8 are byte 1 bits 0 to 7, G9 to G16 byte 2, G17 and G18 byte 3 bits 0 and 1; byte 3 bit 2 is the Game mode switch, bits 4 to 6 M1 to M3, bit 7 MR. Byte 4 bits 0 to 4 are the LCD's five buttons, bit 5 headphone mute, bit 6 mic mute (only reported when the keyboard's own audio isn't used, C22D). The keyboard switches no banks itself: software lights the M keys through feature 0x04 (M1 0x80, M2 0x40, M3 0x20, MR 0x10). The light key isn't in report 0x03: input report 0x04 bit 2 says the backlight is off, and the keyboard ignores colour writes while it is.

Before reading report 0x03 the driver sets feature 0x01 to 18 zeros ("disabling keyboard emulation for the G-keys"). The owner's report already reads 0x01 as 18 zeros. Maybe one byte per G key, what it types by itself; not known.

Next for the bindings: read report 0x03 while G-Lite runs (a reader like `ButtonSpy`), switch the set and light the M key on M1 to M3, and send the bound action with `SendInput` (which can't reach an app running as administrator unless G-Lite is too). To try on a G510 first: does report 0x03 come on Windows without LGS, and does a GET_REPORT of it answer (the Game view's read).

Not known yet:

- whether `05 R G B` written from Windows changes the colour (the Linux driver does the same)
- whether the colour stays after a power cycle, or after unplugging
- whether the keyboard keeps a colour per M key itself, or LGS sent it on each M press (G-Lite keeps one per M key, sent when you pick it)
- what the other feature reports do

### What G-Lite does now

`Devices.Scan` lists a G510 (any HID interface with PID C22D or C22E) as a `FoundDevice` with `PlainHid`, and skips it in the HID++ scan. When it finds the vendor collection (usage page FF00), that becomes its `Path` and it gets `G510Page` (above); otherwise the info page, and nothing is written to it. Its report (`Report.PlainHidReport`) lists every HID collection of the keyboard: its usage, its report lengths, its feature report ids, and the value of each feature report read with `HidD_GetFeature`. That only reads. Collections Windows holds (the keyboard itself) are opened without access, so their layout is listed but reads may fail.

## G512 X 75

Now supported with live lighting: see [G512X.md](G512X.md). What follows is the plan from before its report.

USB 046D:C35F, wired, 2025, with TMR (magnetic) switches and adjustable actuation. The G512 X 98 is its full-size sibling. It speaks HID++ 2.0 at index 0xFF: G-Lite already finds it and shows the info page (firmware "U1").

Its feature list isn't published anywhere. If its report shows 0x8071, 0x8081, 0x8040 and 0x8101 like the G515:

1. Open `KeyboardPage` from the features rather than the name ("G515" in `FoundDevice.IsG515`).
2. Add `app/models/g512-x-75.json`, with the 0x8081 id of each key from the report's lit ids, then checked by lighting keys one by one.
3. Check the screen over a direct USB link (index 0xFF, no receiver).
4. Compare its onboard files with the G515's before allowing Save. If they differ, start with live lighting only, like the G915.

Adjustable actuation is another feature with an unknown protocol. Leave it out.

Next: ask for its report (Report on its info page).
