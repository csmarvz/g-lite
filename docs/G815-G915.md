# G815 and G915 support

How to add the G915, the G915 TKL and the G815, the wired G915, to G-Lite. It builds on [device-research.md](device-research.md). Facts come from Solaar's G915 dumps, OpenRGB's G915 driver and libratbag's device files. They are written down here so the code can be ours: no code is copied from Solaar or OpenRGB (GPL).

Status: live lighting and Save to keyboard work on a real G915 TKL (a Swiss keyboard, 408E, firmware MPK 14.02, tried on 2026-11-17; see "Tested on a G915 TKL" and "Save to keyboard" below). The full-size G915 is still untested. The G815 works on a real keyboard (USB C33F, firmware U1 31.02, tried on 2026-11-20): live lighting, Save and Restore, M1–M3 (switched from G-Lite and followed when pressed), the brightness key and its five levels, G1–G5 bindings and the Game mode key's list; see "The G815" below. "To check" marks what a real keyboard has yet to confirm.

## Scope

First version, on the same screen as the G515:

- Effect, colour, speed, direction and brightness, live.
- The logo follows the keys.
- Until it's saved, G-Lite keeps the lighting as `lighting.<device>` in `settings.txt` and sets it again when G-Lite starts and each time the screen loads. Turning the keyboard off and on behind its receiver doesn't trigger it. Picking None (or Revert with None selected) releases the lighting and forgets it.
- Save to keyboard, in the onboard profile, with idle dim and turn-off (see Saving).
- Battery, from the voltage.
- Report, as on every device.

The light ids of the keys outside the main block come from G HUB's table (via Lghub's `perkey.py`) and the zone list in G HUB's G915 package: logo 0xD2, brightness key 0x99, Previous 0x9E, Play 0x9B, Next 0x9D, Mute 0x9C, G1–G5 0xB4–0xB8.

Not planned: per-key colours (0x8081), host switching (0x1814). Onboard profiles, G keys and macros are planned in [G815-plan.md](G815-plan.md); MR (0x8030) is left alone.

The G915 X (2024, USB C356) is a different keyboard with other features: see [G915X.md](G915X.md).

## Tested on a G915 TKL

What the keyboard showed, with a scratch probe sending one call at a time:

- **Clusters:** 0x8071 fn 0 `FF FF 00` answers `FF 00 02 00 02 00 04`: two clusters. Cluster 0 (`00 FF 00` gives location 2, 4 effects) is the logo: Off, Static, Cycle, Breathe (ids 00, 01, 03, 0A). Cluster 1 (location 1, 7 effects) is the keys: 00, 01, 0A, 03, 04, 0B, and 0C, which G-Lite doesn't offer (on the G815 it freezes the running effect, see "The G815"). Byte 6 of each cluster's info is 0: neither cluster can store an effect, so flags 0x03 won't save.
- **Live effects work in onboard mode.** Host mode (0x8100 fn 1 `02`) isn't needed. `01 03 04` and OpenRGB's `01 03 07` both work.
- **Power modes:** 0x8071 v0 has fn 7 and fn 8. fn 7 reads `00 00 00 00 3C 01 2C`: power save after 60 s, off after 300 s. With `01 03 04` held, the keyboard doesn't dim at 60 s, but still turns off at 300 s, and wakes on its own onboard lighting in power mode 3 (off), ignoring every effect until fn 8 `01 01 00` sets full power. `G915Lighting.Claim` sends it after fn 5, so every change shows. Without power-mode control (`01 01 04`), the keyboard runs its modes itself and never shows G-Lite's lighting again after dimming. Released (`01 00 00`), it runs its profile's lighting and dims at 60 s.
- After a sleep, the keyboard came back on G-Lite's last lighting at a key press.
- **Layout:** 0x4540 reads 0x0D on the Swiss keyboard: ISO. Live keyboards read it too now. On the TKL's top row, the brightness key (0x99) sits above F4 and the media keys above F9–F12. The LIGHTSPEED, Bluetooth and game mode buttons (above F1–F3) aren't lit; the picture shows them dark.
- 0x8071 fn 2 answers error 05, fn 3 error 02; fn 4 reads `00 00 00 62 35`, fn 6 zeros. Not used. fn 3 is the startup and shutdown effect, `<0 get, 1 set> <capability BE16>` (0x0001 startup, 0x0040 shutdown, Logitech's x8071 spec via PeriHub), so an all-zero request is an invalid argument.

## The devices

| Keyboard | Wireless id | USB id | Bluetooth id | Size |

| G915 | 407C | C33E | B354 | Full size |
| G915 TKL | 408E | C343 | B35F | TKL |

Solaar also lists a 407E dump, a later G915 revision with the same features.

- Over LIGHTSPEED the keyboard sits behind its own receiver (C541) at device index 1, like the G515 behind C547. The scan already handles receivers.
- Over USB it answers at index 0xFF, like the PRO X headset dongle.

## Features

From the G915 TKL (408E) and G915 (407C) dumps. Both have the same list. OpenLogi's G915 recording (407C behind C541, `fixtures/devices/g915-001`) confirms it: 0x8071 version 0, 0x8081 version 2, 0x8040, 0x8100, 0x8060, 0x1001 version 3, 0x4540, and no 0x8101.

| Feature | Use |
|---|---|
| 0x8071 RGB effects | Effects, live |
| 0x8040 brightness | Brightness, live (0–100), the same as the G515 |
| 0x8100 onboard profiles | Saving, like the mice |
| 0x1001 battery voltage | Battery. The scan already reads it. |
| 0x8081 per-key lighting | Not used |
| 0x4540 keyboard layout | Not used yet. It would pick ANSI or ISO for the picture. |

There's no 0x8101, so none of `G515Profile.Read`, `Store`, `Restore`, `Claim` or `Activate` applies. They all use 0x8101.

## Lighting

### Clusters

0x8071 has two clusters on the G915: 0 is the logo, 1 is the keys (confirmed on the TKL). Solaar shows them as "LEDs Logo" (0) and "LEDs Primary" (1). The G515 has one cluster, 0, the keys. G-Lite reads them and takes the one with the most effects as the keys.

### Effects

Each cluster lists its effects with fn 0 (cluster, effect index), which returns the effect id. `G515Profile.Preview` already looks the index up this way. The G915's ids are older than the G515's, so the parameters sit elsewhere.

Parameter bytes, after the cluster and effect index, by effect id:

| Id | Effect | Colour | Period (ms, 2 bytes, big endian) | Intensity | Other |
|---|---|---|---|---|---|
| 0x00 | Off | | | | |
| 0x01 | Static | 0–2 | | | byte 3 = 0x02 |
| 0x02 | Pulse | 0–2 | | | speed at 3 |
| 0x03 | Cycle | | 5–6 | 7 | |
| 0x04 | Wave | | see below | | direction |
| 0x0A | Breathe | 0–2 | 3–4 | 6 | |
| 0x0B | Ripple | 0–2 | 4–5 | | period 2–200 |
| 0x15 | Cycle (G515) | | 6–7 | 8 | byte 1 = 0xFF |
| 0x16 | Wave (G515) | | 6–7 | 8 | direction 9, byte 1 = 0xFF |
| 0x17 | Ripple (G515) | 0–2 | 6–7 | | byte 3 = 0xFF |

- The G915 is expected to report 0x01, 0x0A, 0x03, 0x04 and 0x0B for the keys, and Off, Static, Cycle and Breathe for the logo. OpenRGB's G915 driver sends its effects with the 0x03 and 0x0B layouts above, and Breathe like the G515.
- Wave 0x04 uses OpenRGB's layout: the period's low byte at 6, the direction at 7, the intensity at 8 and the period's high byte at 9. The G915 TKL's own profiles store it this way (`04 FF 00 00 00 00 FF B8 01 64 0B`: 3000 ms, direction 1, 100), with `FF` in bytes 0 and 5, where G-Lite sends 00.
- Wave directions: G-Lite sends the G515's values (6 left, 1 right, 3 centre out, 8 centre in). OpenRGB only sends 1. Tried on the G815 on 2026-11-21, 0 to 10: 1 right, 2 down, 3 centre out, 6 left, 7 up, 8 centre in, and 0 cycles through every direction; 4, 5, 9 and 10 leave the wave as it was. Each one restarts the logo's Cycle, which then runs out of step with the keys. The G815 screen offers Up, Down and All too (`KeyboardKinds.VerticalWave`); the G915s wait for a try on a real one.
- Speeds: OpenRGB uses 1000 to 20000 ms for Cycle, Wave and Breathe, and 2 to 200 for Ripple, the same ranges as the G515.

### Live and saved

- `G515Profile.Claim` sends 0x8071 fn 5 `01 03 04` to take software control. OpenRGB sends `01 03 07` on the G915. The last byte only picks events (bit 0 effect sync, bit 1 user activity, bit 2 no-activity timeout), so both should work. See [lighting-control.md](lighting-control.md).
- `G515Profile.Preview` ends each effect with a 0x01 byte. Per the 0x8071 spec (via OpenLogi), bit 0 is "apply in RAM" and bit 1 is "store in EEPROM". So 0x01 is live only, and "not saved" is right. OpenRGB's note that the G915 ignores an effect with that byte at 0 fits: 0x00 asks for neither.
- Don't change the 0x8100 onboard mode. OpenRGB keeps the G915 TKL in onboard mode, because host mode breaks the G keys on its F row.
- Release, when leaving the page: 0x8071 fn 5 `01 00 00`, as on the G515. Without 0x8101 there is no fn 6 to send.

### The logo

The logo has fewer effects. When the keys get an effect the logo lacks, use the closest one, as OpenRGB does:

| Keys | Logo |
|---|---|
| Off, Static, Breathe, Cycle | The same |
| Wave | Cycle |
| Ripple | Static, in the ripple's colour |

## Saving

### Storing the effect

Try this first. Sending the effect with flags 0x03 (apply and store in EEPROM) may save it with no profile layout to work out. Before offering it, read 0x8071 fn 0 `<cluster> FF 00`: byte 6 says whether the cluster can store effects. Send 0x03 only on Save, never on each preview. To check on a real keyboard: it keeps the lighting after a power cycle with G-Lite closed, and the onboard profile doesn't override it. Details in [lighting-control.md](lighting-control.md).

Idle dim and sleep may be 0x8071 fn 7 (seconds to power save and to off) rather than in the profile. But the G915 reports 0x8071 version 0, and fn 7 comes from the v4 spec. A report with fn 7 would tell.

### The onboard profile

Storing the effect won't work: both clusters report no storage (byte 6 is 0). The G915 TKL's report gives the profile:

- 0x8100 info `01 04 01 03 03 0F 10 00 FF …`: profile format 4, 3 profiles, 0x10 sectors of 255 bytes. Onboard mode, profile 0001 active.
- The directory (0000) uses G HUB's entries: `00 01 01 FF 00 02 01 FF 00 03 01 FF`.
- Byte 0 the report interval (1 ms). Bytes 0x1C–0x1F `3C 00 2C 01`: 60 and 300, little-endian, the same times fn 7 reads: power save and off. Confirmed: saved at 15 s and 1 min, the keyboard dimmed and turned off at those times.
- Buttons from 0x20, 4 bytes each: F1–F12 are G keys mapped to `80 02 00 3A`…`45` (the key usages), then M1–M3 as `90 0D FF 01`…`03`. Profile 1's G-shift layer at 0x60 points to macros in sector 0004.
- **In G-Lite:** the Bindings view edits F1–F12 as the G815's edits G1–G5 (same records, saved with Save to M1), marked experimental and shown only when 0x8100 counts 15 slots. The full-size G915's G1–G5 the same way, assumed laid out like the G815's (G1–G5 then M1–M3, 8 slots) and shown only when it counts 8. Neither has been tried on a keyboard.
- The name at 0xA0 (UTF-16, "PROFILE_NAME_DEFAULT").
- Four LED records of 11 bytes from 0xD0: 0 the logo (cluster 0), 1 the keys (cluster 1), 2 and 3 the same at half intensity, probably the power-save lighting. Profile 3 has Cycle on the logo and Wave on the keys, which the logo can't do.
- CRC-16 in the last two bytes, the same as `MouseProtocol.Crc` (checked on two sectors). The factory profiles (0101–0103) end in `FF FF`.

### Save to keyboard

Built on this layout and tried on a real G915 TKL (`G915Lighting.ReadProfile`, `Build`, `Store`, `FactoryLighting`):

- Save reads the active profile (onboard mode, format 4, a user sector 0001–00FF, a good CRC, else it refuses), backs it up under `backups\<device>\` (like `g915tkl`), and changes only records 0–3, the two idle times and the CRC. Records 0 and 1 are the clusters' effects as `G915Lighting.Encode` sends them live; 2 and 3 the same with the intensity at Dim to (the colour scaled for Static and Ripple, which have none), as the keyboard's own profiles do. `MouseProtocol.WriteSector` writes it and reads it back, fn 3 loads it, and fn 5 `01 00 00` gives the lighting back so the keyboard runs it and its power save.
- Once saved, nothing is kept in `lighting.<device>`: the screen reads the profile and shows "Matches the keyboard". A lighting changed live and not saved is kept and sent again as before. While G-Lite holds the lighting, the keyboard doesn't dim (see Power modes above).
- The normal records always get intensity 100, like live lighting: a profile G HUB saved at a lower intensity (the G915 TKL's profile 1 has Cycle at 50) comes back brighter once G-Lite saves it, since brightness is 0x8040's.
- Dim after and Turn off after are the profile's seconds at 0x1C and 0x1E (the keyboard dimmed and turned off at the saved times). 0 isn't never: saved as 0, the G915 TKL dims and turns off at once. So the G915 screens don't offer Never, and `G915Lighting.Build` refuses 0.
- Backups lists the profile's backups and Restore the factory lighting: it copies only the lighting records and idle times of the factory copy (0x0100 + the sector, read only) into the profile, so the rest, like G-shift macros, stays.

When the layout is known:

- Reuse `MouseProtocol.ReadSector`, `WriteSector` and `Crc`.
  - They never write sector 0x0000 or 0x0100 and up.
  - They read back after writing.
- Change only the LED records and the CRC. Keep every other byte.
- Back up the sector before each save, under `backups\g915\`.
- Reload with fn 3, as the mouse does.
- Idle dim and sleep: look for them in the dump. The G515 keeps them at bytes 2–5 of its profile.

## The G815

The G815 (USB C33F) is the wired G915: Solaar's dump lists 0x8071, 0x8081, 0x8040 and 0x8100. `IsG915` accepts its name and it gets its own picture (`g815.json`, from Logitech's drawing: the logo above the G keys, M1–M3, MR, Game mode and brightness, the media keys on the F-key row above the numpad, a right Win key where the G915 has Fn), with presets under `profile.g815.`. Its report confirms it (below).

### Its report

A G815's report (USB C33F, firmware U1 31.02, a Swiss keyboard: 0x4540 reads 0x0D) came on 2026-11-18, replaced by one from 2026-11-20 ([reports/g815-c33f.txt](reports/g815-c33f.txt)). Between the two, profile 1's lighting records became the factory copy's (Cycle and Wave, the power-save records at intensity 50, CRC D489 where it was C034), as Restore the factory lighting writes them; the other profiles are unchanged. No macros: no button or G-shift entry starts with `00`, so the report reads no macro sector.

- **Features:** 0x8071 v0, 0x8081 v2, 0x8040, 0x8100, 0x8060, 0x4540, 0x8010 (5 G keys), 0x8020 (3 M keys), 0x8030, no 0x8101 and no battery. `IsG915` takes it.
- **Clusters:** the same as the G915 TKL. Cluster 0 (location 2) has Off, Static, Cycle and Breathe (00, 01, 03, 0A); cluster 1 (location 1) has 00, 01, 0A, 03, 04, 0B and 0C. Byte 6 is 0 on both: no stored effects.
- **Lit ids:** every key id 00–6F, the brightness key 0x99, the media keys 0x9B–0x9E, G1–G5 0xB4–0xB8 and the logo 0xD2. The same ids as the full-size G915's picture; the right Win key is 0x6F, the id the G915's Fn key has. M1–M3, MR and Game mode aren't lit (their LEDs are white), so `g815.json` gives them `--`.
- **0x8100 info** `01 04 01 03 03 08 10 01 00`: profile format 4, 3 profiles, 8 buttons (G1–G5, M1–M3), and sectors of 256 bytes (`01 00`), where the G915 TKL has 255. Onboard mode, profile 0001 active.
- **The directory** uses libratbag's entries (`00 01 01 00`, then `FF FF 00 00`), where the G915 TKL has G HUB's (`00 01 01 FF`). Both read the same.
- **The profiles** have the G915 TKL's layout: the buttons from 0x20 (G1–G5 as F1–F5 in profile 1, `80 02 00 3A`…), the four lighting records at 0xD0, then `FF FF` and the CRC in the last two bytes (checked: rebuilding profiles 1 and 2 of the first report gives their CRCs C034 and 74A5). `ReadProfile` takes the size from the info, so it reads and writes 256 bytes.
- **No idle times:** 0x1C–0x1F are 0 in all three profiles and in the factory copies. Records 2 and 3 are copies of 0 and 1 in the profiles G HUB wrote; the factory copies have them at half intensity. So the G815 (`KeyboardKinds.NoIdleTimes`) hides Dim after, Dim to and Turn off after, and `G915Lighting.Build` keeps the profile's idle bytes and writes records 2 and 3 as copies, like G HUB.
- G HUB's profiles have intensity 0 in Cycle and Breathe (`03 … 08 34 00`, `0A 00 DC FF 0B B8 00 00`), where the factory copies have 100 (0x64). Tried live on 2026-11-21: 0 looks the same as 100, and lower values dim Cycle, Breathe and Wave, smoothly as far as could be seen. The G815 screen has an Intensity slider (`KeyboardKinds.Intensity`): it reads the profile's intensity (0 shows as 100) and saves the one set. The G915 TKL still writes 100.
- **Effect 0x0C** (cluster 1's seventh effect; fn 0 gives capabilities `00 1B` and `02 34` where the others have their default period): sent live on 2026-11-21, with zeros and with Breathe's, Wave's and Cycle's layouts, it freezes the effect that was running. Colour, speed and intensity change nothing, brightness still works. Not offered. G HUB lists "Verticool" under "Effects on device", and its Echo Press, Starlight, Audio Visualizer and Screen Sampler are drawn by G HUB key by key.
- Sector 0100 isn't a factory directory: it holds what looks like firmware data. The factory profiles are at 0101–0103 and end in `FF FF FF 00`. `FactoryLighting` reads only 0100 + the sector.
- **Reloading a profile written again** (tested on 2026-11-20 with a probe that sent only these calls): the G815 acks 0x8100 fn 3 for the profile it runs but keeps running its old copy, so after a restore G-Lite showed the factory lighting while the keys stayed on the saved Static red, until an M key was pressed. Waiting 300 ms before fn 3 didn't change it. Loading another profile and coming back (fn 3 `00 02`, then `00 01`, with or without a wait) worked, flashing M2. Leaving onboard mode and coming back after the hand-back (fn 1 `02`, then `01`) worked twice, with a barely visible flash of M1: `G915Lighting.Store` does that on the G815 (`KeyboardKinds.ReloadThroughHostMode`). Not tried: sending the effect live after the hand-back. The G915 TKL reloads with fn 3 alone.
- **While G HUB runs** (seen on 2026-11-21): the G815 is off its onboard profiles, 0x8100 fn 2 answers 2 and fn 4 `00 00`, so G-Lite finds no M1–M3 and no G keys and Save would be refused. Closing G HUB put it back on them. G-Lite says so in red and turns Save off (`KeyboardPage.takenOver`).
- **Tested through G-Lite on 2026-11-20:** Save to keyboard and Restore the factory lighting, with the mode switch: the keys follow the saved or restored lighting at once.
- **The keyboard's own lighting keys** (tried on 2026-11-21): brightness + 8 on M1 turned the keys static green, and the next report still had M1's saved wave, byte for byte. The change is live only and isn't written to the profile, so G-Lite keeps showing the saved lighting. Nothing to handle.
- **Power modes** (report of 2026-11-21): 0x8071 is version 0, but fn 7 and fn 8 answer. fn 8 reads mode 1 (full power), and fn 7 is all zeros: no power save or off timers, as the profiles have none. So `Claim`'s fn 8 call, which sets full power, reaches a function that exists. fn 5 read `00 00 00`: no software control while G-Lite only showed the onboard lighting.

### Macros

G HUB, in onboard memory mode, saved macros and bindings to profile 1's G keys on 2026-11-20; with G HUB closed, each key did what was set. [reports/g815-c33f.txt](reports/g815-c33f.txt) (its 11:32 version, in git history) holds the result. First `asd` on G1 (made in G HUB's editor, its default 50 ms delays), then: G2 G HUB's System copy, G3 a media key, G4 left click, G5 a long typed text (G HUB offers no text macro).

**What G HUB makes a macro.** Only G1 and G5 became macros. G HUB saved the other three as plain bindings, the format of `app/Buttons.cs`:

- G2 System copy: `80 02 01 06`, the key C (usage 06) with modifier `01`, left Ctrl. A Ctrl+C typed as a macro couldn't be saved to the keyboard.
- G3: `80 03 00 E2`, the media usage E2 (Mute).
- G4 left click: `80 01 00 01`, mouse button bit 0.

**The button entry** of a macro is `00 <sector> <offset>`: `00` a macro, then the sector (G1 `00 04 00 00`, sector 0004 at 0; G5 `00 04 00 22`, at 0x22), then the byte offset in it, 2 bytes big endian.

**The G-shift layer** at 0x60, `FF` before, is filled with a copy of the buttons. A macro gets a second copy: G-shift G1 is `00 0C 00 2C`, `asd` again in sector 000C. G-shift G5 is `00 04 00 21`, the `FF` that ends the first macro: an empty macro, probably for want of room for a second copy of the long one.

**Macro sectors** are 256 bytes like a profile, with the profile's CRC-16 in the last two bytes, and aren't in the directory. A free sector is one neither the directory nor a button points to; 0x8100 fn 0 byte 6 gives 16 sectors, and the unused ones read all `FF`, or all `00` (000D–000F, without a CRC). Macros start at even offsets: `asd` ends with `FF` at 0x21 and the next starts at 0x22; in 000C one ends at 0x2A, 0x2B is `FF`, the next starts at 0x2C.

**The steps**, then `FF` to end the macro:

- `43 <modifiers> <usage>` key down, the USB usage (04 A, 16 S, 07 D); the modifiers byte is 0 in every step seen.
- `44 <modifiers> <usage>` key up.
- `40 <ms, 2 bytes big endian>` wait: `40 00 32` is 50 ms, between every two steps, none after the last.
- `60 <sector, 2 bytes> <offset, 2 bytes>` go on at that sector and offset: a macro that doesn't fit its sector ends it with `60 00 05 00 00` and goes on at the start of 0005. Then `FF` up to the CRC. The long text on G5 runs from 0004 at 0x22 through 0005 to 000C, each ending with a `60` to the next and the next starting with the wait that was due.
- So `asd` is `43 00 04 40 00 32 44 00 04 40 00 32 43 00 16 40 00 32 44 00 16 40 00 32 43 00 07 40 00 32 44 00 07 FF`: 34 bytes.
- The steps keep the typing as recorded: keys overlap (`43` I, `43` S, `44` I, `44` S), and a Swiss keyboard's Y gives the US usage 1D (Z). At 12 bytes a character with the waits, the text takes nine sectors.

G HUB also rewrote profile 1's other bytes: 0x0D–0x11 from `FF` to `00`, and the keys' lighting record from `04 FF 00 00 00 00 FF 34 01 64 08` to `04 00 00 00 00 00 00 34 01 64 08`, with the CRC.

Not seen yet: a modifier inside a macro, a media key or mouse button inside a macro, waits above 255 ms, G HUB's repeat options, and what the G915 TKL's entries 2 bytes apart (`00 04 00 00`, `00 04 00 02`…) point to. G HUB stopped saving macros to the G815 after these, so the rest is from libratbag.

**libratbag's list** (MIT, `src/hidpp20.h`, read 2026-11-20; it parses only 00, 40, 43, 44, 60 and FF, writes no macros and has no timing):

| Byte | Step | libratbag's length |
|---|---|---|
| 00 | no-op (waits one step) | 1 |
| 01 | wait for release | 1 |
| 02 | repeat while pressed | 1 |
| 03 | repeat until cancelled | 1 |
| 20 | wheel | |
| 21 | horizontal wheel (AC pan) | |
| 40 | delay, 2 bytes big endian | 3 |
| 41, 42 | mouse button down, up | |
| 43, 44 | key down, up: modifiers (`01` Ctrl, `02` Shift), usage | 3 |
| 45, 46 | media (consumer) down, up | |
| 60 | jump | 3 |
| 61 | pointer move | |
| FF | end | 1 |

Two things differ from the G815: libratbag reads the jump as 3 bytes, `60 <offset> <sector>`, where the G815's are 5 (`60 00 05 00 00`, sector and offset 2 bytes each); and it never lets a step cross 16 bytes, where the G815's `asd` has steps at 0x0F–0x11. Its macro entry `00 <sector> 00 <offset>` matches the G815's for sectors and offsets under 256. The repeat steps (01–03) are probably what G HUB's "repeat while holding" and "toggle" write, at the start of the macro; this is unconfirmed.

### Logitech's manual

From the G815 manual on manualslib ([guide 3614220](https://www.manualslib.com/guide/3614220/logitech-g815-manual.html), read on 2026-11-20). Its text says "G915" in places and names Logitech Gaming Software: it was copied from the G915's manual, so each fact is the G915's too, and may not all hold on the G815. The full PDF (the page's download link) wasn't read.

- **Onboard lighting effects:** hold the brightness key and press a number. 1 to 4 Colorwave (left to right, right to left, centre out, bottom up), 5 Color cycle, 6 Ripple, 7 Breathing, 8 and 9 two user-stored lightings that G HUB saves, 0 cyan blue; minus and plus slow and speed up the effect. The report says neither cluster stores effects (0x8071 fn 0 byte 6 is 0), so where slots 8 and 9 live isn't known. Bottom up is direction 7 (see Effects).
- **M keys:** M1–M3 switch profiles on their own, and the keyboard sends an 0x8100 event (fn 0, as the mice do), so G-Lite's screen follows at once (tried on 2026-11-20). The running profile's own M key blinks the keyboard but sends no event, and 0x8071 fn 5 (control `03 04`) and 0x8100 fn 4 read the same before and after (probed 10 times a second while a live effect ran, 2026-11-21): G-Lite can't see that press, so a live effect carries on. Clicking the running profile in G-Lite's footer stops it instead.
- **Brightness key:** cycles through brightness levels (five: 0x8040 fn 0 byte 2 is the key's level count, see below). G-Lite follows it: the keyboard sends an 0x8040 event, and G-Lite reads the level then (and when the window comes to the front).
- **Five brightness levels** (2026-11-20, from `log.txt`): 0x8040 keeps only 100, 50, 25, 12 and 0, the levels the key steps through; any other value drops to the one below (90, 93 and 96 read back 50; 29 reads 25; 24 reads 12). Its fn 0 answers `00 64 05 03` like the G515's, which takes any value. Per Logitech's x8040 spec, as PeriHub reads it: bytes 0–1 the maximum, byte 2's low nibble the number of levels the brightness key steps through (5), byte 3 flags (0x04 on/off set apart from brightness, 0x10 transient: a set brightness isn't kept over a power cycle), bytes 4–5 the minimum; Solaar steps by halves, the G815's 100, 50, 25, 12, 0. What fn 0 doesn't say is whether a set value snaps to a level: the G815's does, the G515's doesn't. G-Lite's slider stops at the five levels, unmarked (`KeyboardKinds.BrightnessLevels`; the ticks were dropped on 2026-11-21). Finer steps by dimming the effect were tried on 2026-11-21: the level above, with the intensity (or the colour, for Static and Ripple) lowered to match. They didn't look right: 60% (level 100 at intensity 60) was darker than 50%. So the slider keeps the five levels.
- **Game mode key:** turns off the Windows and Menu keys, and its LED is lit while it's on. G HUB can change which keys it turns off, probably through 0x4522, which the report lists. Seen in G HUB on 2026-11-21: both Windows keys and Menu are off by default and can't be turned back on; any other key with a standard usage can be added; G1–G5, M1–M3, MR, Game mode, brightness, the media keys and the volume roller can't be picked, which fits a feature named "disable keys by usage". Tried on 2026-11-21: W added in G HUB, G HUB quit, Game mode on: W does nothing. After unplugging the keyboard, W types again: the keyboard keeps the list only while powered, so an app has to send it again each time the keyboard connects.
  - **0x4522 per [OpenLogi](https://github.com/AprilNEA/OpenLogi) (Apache-2.0, `disable_keys_by_usage.rs`):** fn 0 reads the capacity (byte 0, the most usages it can hold); fn 1 disables the HID keyboard usages given, up to 16 per long report, ended by `00` or a full report, and adds them to those already disabled; fn 2 enables the usages given; fn 3 enables all. There's no function to read the list back. Solaar names it `KEYBOARD_DISABLE_BY_USAGE` and SignalRGB `DisableKeysByUsage`, but neither calls it.
  - **[OpenGHub](https://github.com/Slyvan25/OpenGHub) (MIT, `docs/hidpp.md`)** tried it on a G915: fn 0 gave a capacity of 255, but disabling A, S and D with fn 1 or 2, in onboard and host mode, with Game mode on or off, left every key working, so it blocks keys in software instead. Not known why; the W test above says the G815 applies a list on its own.
  - **Tried on the G815 on 2026-11-21** with a probe that sent only 0x4522 calls, G HUB closed: fn 0 answers `FF` (255 usages). fn 1 `1A` (W): W types with Game mode off and doesn't with it on, and the Windows key stays off. fn 3 clears it: W types in Game mode again, Windows still off. fn 1 `0E` (K): only K is off in Game mode, W types. fn 2 `0E`: K types again. So the list only holds the keys added on top of the Windows and Menu keys, which the firmware turns off by itself, and it applies only while Game mode is on.
  - **In G-Lite** (2026-11-21): the G815 screen's Game view sets the list (`GameModeKeys`), sends it again when the keyboard connects, and keeps it in presets. Tried on a real G815 the same day: the keys picked are off in Game mode, a replug gets the list back, so does G HUB opening and closing, and a preset sets its keys.
  - **The G515 TKL** has 0x4523 instead (fn 0 takes 16 bytes) and 0x1B10, a list of its controls. Tried on a real G515 TKL (Swiss) on 2026-11-23, G HUB closed:
    - 0x1B10 fn 0 answers `80` (128 controls); fn 1 with an index gives eight big-endian control ids from that index (`00` after the last, error 02 at 0x80). The list is in `FakeHidpp.ControlList`.
    - 0x4523 fn 0 with a bitmap turns off control i (bit i % 8 of byte i / 8) while Game mode is on: byte 7 `FF` turned off A, D, G, J, L, à, Enter and End, controls 0x38–0x3F. The reply is zeros.
    - The ids are Logitech's: letters 0x0122 + n, digits 0x0142 (0) to 0x014B (9), and Solaar's names for others (F1 0x00F6, F2–F8 0x00EF–0x00F5, Tab 0x010C, Caps 0x010D, Home 0x0118). The others were placed from where they sit in the list, which follows the key matrix: a row of keys takes turns between two groups of eight (` at 0x08, 1 at 0x18, 2 at 0x09, 3 at 0x19 and so on). Space, Up, Down, left Alt and AltGr placed that way were confirmed in G-Lite. Ids where JIS keyboards have extra keys (0x017C, 0x017E, 0x017F, 0x0180) and 0x0159, 0x0185, 0x018A are left unmapped.
    - Unlike the G815, the G515 doesn't turn the Windows and Menu keys off by itself: with an empty list both work in Game mode. They're controls like the others.
    - The keyboard forgets the list when turned off, like the G815, so G-Lite sends it again whenever it connects. Turned off and on within a few seconds, it never looks gone to a scan, so the receiver's connect notice (0x41) sends it too.
    - In G-Lite: the G515's Game view picks keys as on the G815, Windows and Menu included. The G915 X and G915 X TKL (0x4523 and 0x1B10 too) get the same view, marked experimental: their control list may differ, and only ids G-Lite knows are sent. The G512 X 75 lists both features too, at the same versions, and gets the same experimental view.
  - **The G915 and G915 TKL** list 0x4522 too (Solaar's G915 dumps, the G915 TKL's report), so their screens have the same Game view, marked experimental: it hasn't been tried on one, and OpenGHub's G915 kept every key working. To check on a G915: pick W in the Game view, turn Game mode on, press W. Their Fn key sits where the G815 has its right Windows key (the same id) and isn't marked always off.
- **Media keys:** previous, play/pause, next and mute, and a **volume roller** for the PC's volume. The roller doesn't light; the key picture shows it above the media keys, from photos (on the G815 and every G915).
- **M1–M3 and onboard memory:** three profiles, picked with M1–M3 in onboard mode, which G HUB selects and which applies when G HUB is closed or not installed. What a profile holds isn't said; the report shows the G keys' bindings and the lighting.
- **MR, recording a macro:** press MR, a G key, type the keys, then MR again. With M2 or M3 active, the same steps record a second and a third macro on that G key. Whether this works without software isn't said. Tried on the G815 on 2026-11-20, in onboard mode: it doesn't. MR doesn't light, and MR, G1, typing `qwe`, MR records nothing: G1 still types what profile 1 binds it to (F1). So MR needs the software to drive it (0x8030, and the G keys taken over by 0x8010), as [G815-plan.md](G815-plan.md) step 5 assumed. With G HUB running, MR works: it lights red when pressed, the G keys green and the other keys white-ish, which G HUB draws itself (probably 0x8030 for MR's LED and 0x8081 for the keys, G1–G5 being lit ids B4–B8). The recorded macro stays in G HUB: with G HUB closed, G1 typed F1 again, and a report right after showed the profiles unchanged (G1 still `80 02 00 3A`, the same CRCs). With G HUB's onboard memory mode on, MR does nothing either: MR only works while G HUB drives the keyboard in host mode. Only a profile G HUB writes to the keyboard's onboard memory would carry a macro, with the macro made in G HUB's editor and assigned to a G key.
- Also listed, with no details: USB pass-through.
