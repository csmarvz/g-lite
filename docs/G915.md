# G915 support

How to add the G915 and G915 TKL to G-Lite. It builds on [device-research.md](device-research.md). Facts come from Solaar's G915 dumps, OpenRGB's G915 driver and libratbag's device files. They are written down here so the code can be ours: no code is copied from Solaar or OpenRGB (GPL).

Nothing here has been tried on a real G915 yet. "To check" marks what a real keyboard has to confirm.

Status: live lighting is built (steps 1 and 2 under Order), and tested against `FakeG915` only.

## Scope

First version, on the same screen as the G515:

- Effect, colour, speed, direction and brightness, live.
- The logo follows the keys.
- G-Lite keeps the lighting as `lighting.<device>` in `settings.txt` and sets it again when G-Lite starts and each time the screen loads, since it can't save it to the keyboard. Turning the keyboard off and on behind its receiver doesn't trigger it. As on the keyboard releases the lighting and forgets it.
- Battery, from the voltage.
- Report, as on every device.

Later, once a real G915's report is in:

- Save to keyboard, in the onboard profile.
- Idle dim and sleep, if the profile has them.
- Its own picture for the G915 full size (numpad, G keys, media strip).

Not planned: per-key colours (0x8081), G keys and macros (0x8010, 0x8020, 0x8030), host switching (0x1814).

The G915 X (2024, USB C356) is a different keyboard with other features. Leave it out until someone sends its report.

## The devices

| Keyboard | Wireless id | USB id | Bluetooth id | Size |
|---|---|---|---|---|
| G915 | 407C | C33E | B354 | Full size |
| G915 TKL | 408E | C343 | B35F | TKL |

Solaar also lists a 407E dump, a later G915 revision with the same features.

- Over LIGHTSPEED the keyboard sits behind its own receiver (C541) at device index 1, like the G515 behind C547. The scan already handles receivers.
- Over USB it answers at index 0xFF, like the PRO X headset dongle.
- Over Bluetooth: untested, and not in the first version.

## Features

From the G915 TKL (408E) and G915 (407C) dumps. Both have the same list. OpenLogi's G915 recording (407C behind C541, `fixtures/devices/g915-001`) confirms it: 0x8071 version 0, 0x8081 version 2, 0x8040, 0x8100, 0x8060, 0x1001 version 3, 0x4540, and no 0x8101.

| Feature | Use |
|---|---|
| 0x8071 RGB effects | Effects, live |
| 0x8040 brightness | Brightness, live (0–100), the same as the G515 |
| 0x8100 onboard profiles | Saving, like the mice |
| 0x1001 battery voltage | Battery. The scan already reads it. |
| 0x8081 per-key lighting | Not used |
| 0x4540 keyboard layout | Not used yet. It would pick ANSI or ISO for the picture. |

There's no 0x8101, so none of `G515.Read`, `Store`, `Restore`, `Claim` or `Activate` applies. They all use 0x8101.

## Lighting

### Clusters

0x8071 has two clusters on the G915: 0 is the logo, 1 is the keys. Solaar shows them as "LEDs Logo" (0) and "LEDs Primary" (1). The G515 has one cluster, 0, the keys.

To check: fn 0 with no effect index returns the cluster count and each cluster's location. Read it rather than assume 0 and 1.

### Effects

Each cluster lists its effects with fn 0 (cluster, effect index), which returns the effect id. `G515.Preview` already looks the index up this way. The G915's ids are older than the G515's, so the parameters sit elsewhere.

Parameter bytes, after the cluster and effect index, by effect id:

| Id | Effect | Colour | Period (ms, 2 bytes, big endian) | Intensity | Other |
|---|---|---|---|---|---|
| 0x00 | Off | | | | |
| 0x01 | Static | 0–2 | | | byte 3 = 0x02 |
| 0x02 | Pulse | 0–2 | | | speed at 3 |
| 0x03 | Cycle | | 5–6 | 7 | |
| 0x04 | Wave | | see below | | direction |
| 0x0A | Breathe | 0–2 | 3–4 | 6 | |
| 0x0B | Ripple | 0–2 | 4–5 | | period 2–200 |
| 0x15 | Cycle (G515) | | 6–7 | 8 | byte 1 = 0xFF |
| 0x16 | Wave (G515) | | 6–7 | 8 | direction 9, byte 1 = 0xFF |
| 0x17 | Ripple (G515) | 0–2 | 6–7 | | byte 3 = 0xFF |

- The G915 is expected to report 0x01, 0x0A, 0x03, 0x04 and 0x0B for the keys, and Off, Static, Cycle and Breathe for the logo. OpenRGB's G915 driver sends its effects with the 0x03 and 0x0B layouts above, and Breathe like the G515.
- Wave 0x04 isn't settled. OpenRGB puts the period's low byte at 6, the direction at 7, the intensity at 8 and the period's high byte at 9. Solaar guesses the 0x16 layout. G-Lite uses OpenRGB's layout. To check on a real keyboard.
- Wave directions: G-Lite sends the G515's values (6 left, 1 right, 3 centre out, 8 centre in). OpenRGB only sends 1. To check.
- Speeds: OpenRGB uses 1000 to 20000 ms for Cycle, Wave and Breathe, and 2 to 200 for Ripple, the same ranges as the G515.

### Live and saved

- `G515.Claim` sends 0x8071 fn 5 `01 03 04` to take software control. OpenRGB sends `01 03 07` on the G915. The last byte only picks events (bit 0 effect sync, bit 1 user activity, bit 2 no-activity timeout), so both should work. See [lighting-control.md](lighting-control.md).
- `G515.Preview` ends each effect with a 0x01 byte. Per the 0x8071 spec (via OpenLogi), bit 0 is "apply in RAM" and bit 1 is "store in EEPROM". So 0x01 is live only, and "not saved" is right. OpenRGB's note that the G915 ignores an effect with that byte at 0 fits: 0x00 asks for neither.
- Don't change the 0x8100 onboard mode. OpenRGB keeps the G915 TKL in onboard mode, because host mode breaks the G keys on its F row.
- Release, when leaving the page: 0x8071 fn 5 `01 00 00`, as on the G515. Without 0x8101 there is no fn 6 to send.

### The logo

The logo has fewer effects. When the keys get an effect the logo lacks, use the closest one, as OpenRGB does:

| Keys | Logo |
|---|---|
| Off, Static, Breathe, Cycle | The same |
| Wave | Cycle |
| Ripple | Static, in the ripple's colour |

## Saving (later)

### Storing the effect

Try this first. Sending the effect with flags 0x03 (apply and store in EEPROM) may save it with no profile layout to work out. Before offering it, read 0x8071 fn 0 `<cluster> FF 00`: byte 6 says whether the cluster can store effects. Send 0x03 only on Save, never on each preview. To check on a real keyboard: it keeps the lighting after a power cycle with G-Lite closed, and the onboard profile doesn't override it. Details in [lighting-control.md](lighting-control.md).

Idle dim and sleep may be 0x8071 fn 7 (seconds to power save and to off) rather than in the profile. But the G915 reports 0x8071 version 0, and fn 7 comes from the v4 spec. A report with fn 7 would tell.

### The onboard profile

If storing the effect doesn't work. The G915's 0x8100 reports profile format 4. `GMouse` only accepts format 3. libratbag and Solaar read format 4 with the mouse layout:

- Report interval at 0, name at 0xA0 (UTF-16).
- LED records of 11 bytes from 0xD0: effect id, then the 0x8071 parameters. Solaar reads four of them, probably keys and logo, normal and dimmed.
- CRC-16 in the last two bytes, the same as `GMouse.Crc`.

The report already reads the 0x8100 info (fn 0), mode (fn 2), the current profile (fn 4) and its sector (fn 5). A real G915 report is enough to work out the layout. Until then there's no Save to keyboard on the G915.

When the layout is known:

- Reuse `GMouse.ReadSector`, `WriteSector` and `Crc`.
  - They never write sector 0x0000 or 0x0100 and up.
  - They read back after writing.
- Change only the LED records and the CRC. Keep every other byte.
- Back up the sector before each save, under `backups\g915\`.
- Reload with fn 3, as the mouse does.
- Idle dim and sleep: look for them in the dump. The G515 keeps them at bytes 2–5 of its profile.

## Order

1. Ask a G915 owner (issue #3) to attach a report and, if they can, a log of a few live changes. The report gives the effect ids per cluster and the profile sector.
2. Build live lighting against `FakeG915`.
3. Check it on a real G915: the effects, Wave's bytes, and that a live change (0x01) is gone after a power cycle.
4. Then saving: first flags 0x03, else the sector in the report.
